# Troubleshooting sync

`skram-vault sync` is `git pull --rebase` against the vault's remote, then
`git push` (README §6). This page covers the merge path a stranger hits on
day one: a conflict in a generated index, a conflict in something you wrote
by hand, and a write that gets refused while git is mid-merge.

## A conflict in a generated index

`lore.md`, `specs.md`, `tickets.md`, and the root `vault.md` are rewritten by
every write, so two machines that wrote different topics between syncs will
often conflict on the same lines of the same index when you `sync`. This is
not yours to resolve: `sync` already handles it. When `git pull --rebase`
conflicts and every conflicted path is a generated index on both sides, sync
aborts the rebase, merges the remote branch instead, rewrites every
configured kind's indexes from the files actually on disk, and commits the
merge:

```
merged remote changes 4a97346 (regenerated 3 indexes)
pulled 2, pushed 0
```

Never hand-edit a generated index to get past a conflict: a file whose
first line is `<!-- generated by skram … -->` is discarded on the next write
or `skram-vault regen` anyway, so a hand fix does not survive.

## A conflict in a topic, spec, or ticket

If the same topic, spec, or ticket was edited differently on two machines
before either synced, that is real work on both sides and `sync` will not
guess for you. It aborts the rebase, aborts its own merge attempt too, and
leaves the vault exactly as it was before you ran it (`git status` inside
the vault shows a clean tree, not a merge in progress):

```
Error: vault: sync conflicts in acme/topic-a.md; resolve by hand: git -C ~/vault merge origin/main
```

Run the `git merge` command it prints, resolve the `<<<<<<<` markers in the
file yourself (in the body; the frontmatter above the markers is untouched
and still parses), `git add` the file, and `git commit`. Then run
`skram-vault sync` again to push the result; it needs nothing further from
you at that point.

## A write refused mid-merge

`skram-vault`'s writes stage and commit only the files they touch, and git
refuses a partial commit while a merge is unresolved. If you stop partway
through the hand resolution above (you ran `git merge` but never finished
it, or a merge conflict came from something other than `sync`), the next
`skram-vault lore write` (or `spec`/`ticket` write) fails with git's own
error, not a friendlier one:

```
Error: git commit: fatal: cannot do a partial commit during a merge.
```

Finish the merge (`git add` the resolved paths, then `git commit`) or give
up on it (`git merge --abort`) before writing again. `skram-vault doctor`
does not detect this state; see below.

## What `doctor` and `lint` do, and do not, catch

`skram-vault doctor` and `skram-vault lint` check the vault's *content*:
frontmatter, statuses, links, and whether the generated indexes are current.
They do not look at git's own state. A vault left mid-merge, or
one with `<<<<<<<` conflict markers sitting in a topic's body, still reports
`[ok]` from `doctor` and `ok` from `lint`: the frontmatter above the
markers parses fine, and nothing walks the body looking for them. A vault
that has diverged from its remote (commits on both sides, sync not yet run)
reports the same way: `doctor` has no opinion on sync state at all.

The one place any of this shows is `git status` run inside the vault
directory, and the error text `sync` or a write command returns. When
something about a vault looks wrong and `doctor` says everything is fine,
check `git status` in the vault next.
