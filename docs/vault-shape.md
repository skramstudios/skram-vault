# The shape of a vault

A vault is an ordinary git repository of markdown files. `skram-vault` is the
only thing that should write to it: every write goes through one commit, keeps
the generated indexes current, and is attributed to whoever made it (you, or
the agent that was driving). Reading it needs nothing: it is files.

```
my-vault/                          a git repo (give it a private remote to share it between machines)
  vault.md                         generated: every namespace, with topic/spec/ticket counts
  lore.md                          generated: every lore topic in every namespace
  shared/                          a namespace every checkout can read
    lore.md                        generated: this namespace's topics
    some-topic.md                  a lore topic
  my-app/                          one namespace per project, product, or area
    lore.md
    .vault-ids.json                the next S-<n> and T-<n> here; committed with the write that used it, so two machines never hand out the same id
    decisions.md                   the decision log (`lore decide` appends to it)
    webhook-retries.md             a lore topic
    specs/
      specs.md                     generated index
      S-0001-checkout-rewrite.md
    tickets/
      tickets.md                   generated index
      T-0001-move-cart-totals-server-side.md
```

Files whose first line is `<!-- generated by skram … -->` are rewritten by every
write. Edit frontmatter and bodies, never an index. A markdown file at the
vault root that is not one of the generated indexes is a lint problem
(`stray-file`), so a README for the vault's own GitHub page goes in
`.github/README.md`.

## Namespaces

A namespace is a directory. It holds what is true of one project or area,
whichever repos that spans: a backend and a frontend repo can share one
namespace, and so one backlog. `shared` is always in scope everywhere.

Which namespaces apply inside which checkout is not stored in the vault. It is
the `repos:` block of `~/.config/skram/config.yaml` on each machine
(README §3), matched by the checkout's git remote, so the same vault serves
different machines with different directory layouts.

A namespace can read from others:

```yaml
vault:
  path: ~/vault
  namespaces:
    my-app:
      uses: [platform]     # reads, search, and indexes in my-app also cover platform; writes never do
```

## The `vault:` block

Everything `skram-vault` reads for itself is under `vault:` in
`~/.config/skram/config.yaml`, beside the `repos:` block that says which
namespaces apply in which checkout (README §3). Only `path` is required.
Where a key has a default it is the value shown, so omitting the key behaves
the same way; the keys that have no default say what happens when they are
left out.

```yaml
vault:
  path: ~/vault                  # required; the vault's git repo (~ expanded, then must be absolute)
  namespaces:
    my-app:                      # one entry per namespace you want to configure
      uses: [platform]           # namespaces this one also reads from
  lore:
    statuses: [Confirmed, Explored, In-progress, Skeleton, Parked]
    template: ~/vault/topic.md.tmpl   # unset: the built-in new-topic template
    decisions: decisions         # the topic id `lore decide` appends to
    index_name: lore.md          # the generated per-namespace index (vault.md is reserved)
  specs:
    statuses: [draft, ready, implemented, superseded]
  tickets:
    statuses: [needs-triage, needs-info, ready-for-agent, ready-for-human, in-progress, done, wontfix]
  sync:
    remote: origin               # the vault's git remote
    branch: main                 # unset: whatever branch the vault is on
```

`specs:` and `tickets:` turn those kinds on by being present at all: `specs:
{}` is enough, and without the key there are no `spec` verbs, no `spec_*`
tools, and no spec resources. `lore` is always on.

## Lore topics

What you learned the hard way and the code does not say: why the retry count
is three, what breaks when the proxy header is missing, which of two fixes
was tried and abandoned.

```markdown
---
title: Webhook retries
summary: The gateway retries three times, then drops silently.
status: Confirmed
related: [gateway-timeouts]
updated: 2026-01-01
---
## Overview

## Findings

## Open Questions
```

- The file name is the topic id (`webhook-retries`). `related` holds other
  topic ids.
- `status` is one of `Confirmed`, `Explored`, `In-progress`, `Skeleton`,
  `Parked` (override with `vault.lore.statuses`).
- `summary` is what search results and the indexes show; an agent decides
  whether to open the topic from it, so write it as the finding, not the
  subject.
- Keys the vault does not know pass through untouched.
- `skram-vault lore write my-app webhook-retries --section "Findings" < body.md`
  replaces one section and leaves the rest; without `--section` it writes the
  whole body. A topic that does not exist is created from the template above.
- `skram-vault lore decide my-app "Use server-side totals"` appends a dated
  entry with its rationale to `my-app/decisions.md`.

## Specs

What you decided to build. Ids are `S-<n>`, allocated per namespace; the file
is `specs/S-0001-<slug>.md`.

```markdown
---
id: S-1
title: Checkout rewrite
summary: Move cart totals server-side so the three clients stop disagreeing.
status: draft            # draft | ready | implemented | superseded
superseded_by:
updated: 2026-01-01
---
## Problem statement
## Solution
## User stories
## Implementation decisions
## Testing decisions
## Out of scope
## Further notes
```

```bash
skram-vault spec new my-app "Checkout rewrite"      # create one; prints the id it allocated
skram-vault spec list my-app                        # every spec here, with its status
skram-vault spec show my-app S-1                    # the file, plus its recent history
skram-vault spec set my-app S-1 --status ready      # move it along the statuses above
```

## Tickets

What is left to do. Ids are `T-<n>` per namespace; the file is
`tickets/T-0001-<slug>.md`. Refer to another namespace's ticket as
`platform/T-4`.

```markdown
---
id: T-1
title: Move cart totals server-side
summary: ""
status: ready-for-agent
category: enhancement    # bug | enhancement
spec: S-1
blocked_by: [T-3]
assignee:                # set by --claim to whoever claimed it
resolution:              # one line, set by close
closed:                  # set iff status is done or wontfix
updated: 2026-01-01
---
## What to build
## Acceptance criteria
- [ ]
## Notes
```

Statuses, in order: `needs-triage`, `needs-info`, `ready-for-agent`,
`ready-for-human`, `in-progress`, `done`, `wontfix`. A ticket is open unless
it is `done` or `wontfix`.

**The frontier** is the list of tickets that can be started now: open,
unclaimed, and every blocker closed. It is the one query an agent needs at the
start of a session:

```bash
skram-vault ticket list my-app --frontier            # this namespace
skram-vault ticket list my-app --frontier --spec S-3 # one spec's own frontier
skram-vault ticket list --all --frontier             # every namespace
skram-vault ticket show my-app T-1                   # the file, plus its recent history
skram-vault ticket set my-app T-1 --claim            # first write of the session
skram-vault ticket close my-app T-1 --resolution "totals computed in /cart, clients read them"
```

## History, sync, and sharing

- Every write is one commit whose author is the detected actor, so `git log`
  in the vault is the audit trail and `git revert` is the undo. The actor is
  `$SKRAM_ACTOR` when you set it, otherwise `claude-code` or `cursor` when the
  write came from one of those, otherwise `$USER` — so a commit says which
  agent, or which person, made it.
- A write (of lore, a spec, or a ticket) syncs the remote around itself: it
  pulls the remote current before it allocates an id or commits, and pushes the
  commit after — so two machines writing to one shared vault never hand out the
  same `T-<n>` or `S-<n>`. The sync is best-effort: if the remote is unreachable
  it warns and still commits locally (an offline write beats no write), and the
  next write or `skram-vault sync` reconciles it. Pass `--no-sync` (or set
  `SKRAM_VAULT_SYNC=0`) to turn it off for the offline or airgapped case.
- `skram-vault sync` is `git pull --rebase` then `git push`, the explicit form
  of what a write does around itself. It commits stale generated indexes itself
  and stops if a topic, spec, or ticket has uncommitted hand edits. A
  `.vault-ids.json` conflict — two machines that each allocated an id before
  syncing — it resolves to the higher counter rather than asking for a hand
  merge, and `skram-vault lint` reports a `duplicate-id` if two files ever share
  one id.
- To share a vault between your machines, give it a private remote and clone
  it on each; point each machine's `vault.path` at its clone. To share one
  with a team, do the same with a repo the team can push to.
- `skram-vault lint` checks every topic, spec, ticket, and index;
  `skram-vault regen` rewrites the indexes after hand edits.
  `skram-vault lore lint` and `skram-vault lore regen` do the same for lore
  alone, and `skram-vault lore index` and `skram-vault lore sync` are the
  same commands as `skram-vault index` and `skram-vault sync`.
